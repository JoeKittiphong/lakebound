# ป้องกันปลาตัวเดียวกินเบ็ดหลายคน

## สาเหตุและแนวทาง

เดิมแต่ละเครื่องเริ่ม population และ RNG ด้วย seed เดียว แต่ตัดสินการกินเบ็ด/เก็บปลาแยกกัน
ปลา ID เดียวและน้ำหนักเดียวกันจึงถูกจับหลายคนได้ และฐานข้อมูลกันซ้ำเพียงต่อผู้เล่น

คงปลาเป็นทรัพยากรร่วมในห้อง โดยมี ID และข้อมูลเกิดที่กำหนดซ้ำได้จาก room seed + fish ID
แยกลำดับสุ่มการเคลื่อนที่/ตัดสินกินเบ็ดตามผู้เล่น ไม่ทำให้ทุกเครื่องเล่นเหตุการณ์เดียวกันเป็นลำดับ
ปลาที่เกิดทดแทนใช้ ID ต่อเนื่องและข้อมูลเดิมได้แม้เครื่องหนึ่งใช้ RNG ไปแล้วต่างกัน

## สิทธิ์และผลจับ

- ก่อนแสดง BITE/สั่น/เปิดเวลาวัดเบ็ด ต้องได้ `claim_fish` จาก Supabase ก่อน
- แถว `(room_id, round_id, fish_id)` มีเจ้าของคนเดียว ตรวจภายใต้ admission lock เดิม
- คนเดียวถือปลาที่กำลังสู้ได้หนึ่งตัว สิทธิ์ 90 วินาที ต่ออายุทุก 10 วินาทีระหว่าง BITE/FIGHT
- ปลาหลุด ยกเลิก หรือออกห้องคืนสิทธิ์; หลุดการเชื่อมต่อแล้ว lease หมดคืนสิทธิ์เอง
- ทุกครั้งที่มีเจ้าของใหม่ออก claim UUID ใหม่ ผลหรือคำสั่งปล่อยที่มาช้าของคนเดิมใช้กับคนใหม่ไม่ได้
- การส่ง catch ต้องตรงปลา เจ้าของ round nonce ชนิด และน้ำหนักตอนจอง
  จับสำเร็จแล้วปลาเป็น consumed ทั้งห้อง ไม่มีใครรับคะแนนปลา ID นั้นซ้ำ
- ส่งผลสำเร็จซ้ำของเจ้าของเดิมยังเป็น idempotent ไม่เพิ่มคะแนน
- ปลาไม่เข้าเงื่อนไขชนิดเป้าหมายยังถูกนำออกจากสนาม แต่คะแนนของกติกานั้นไม่นับ
- Snapshot เดิมส่ง active claims และ consumed IDs แบบ compact ไม่มี Realtime stream เพิ่ม
  อีกเครื่องนำปลาที่จับแล้วออก ปิดการกินเบ็ดของปลาที่คนอื่นถือ และคืนเมื่อสิทธิ์หมด
- กลับเข้าห้องใหม่ข้าม consumed IDs และเติมปลาใหม่ตามลำดับเดิม ไม่สร้างปลาที่ถูกจับแล้วกลับมาซ้ำ

Migration `202611030013_exclusive_match_fish.sql` เพิ่ม private table และ wrapper ที่ตรวจทุก catch
สำรองสถานะปลาที่ระบุได้จาก catch ID เดิมเป็น consumed โดยไม่แก้/ลบคะแนนเก่า
Client เก่าที่ไม่มี claim ส่งคะแนนใหม่ไม่ได้ ต้องเปิดเกมรุ่นแก้
อำนาจยืนยันยังอยู่ที่ Supabase ไม่ใช้ Broadcast เป็นตัวตัดสินสิทธิ์
การเคลื่อนที่ปลาเป็น simulation ของแต่ละเครื่อง ไม่ใช่ระบบจำลองปลาเต็มรูปแบบบน server

## ตรวจสอบ

- PostgreSQL: 147 checks รวม race แย่งปลา/ส่งผลพร้อมกัน, nonce เก่า, หลุด/หมดสิทธิ์,
  ส่งซ้ำ, น้ำหนักเปลี่ยน, เปลี่ยนรอบ, สิทธิ์ตาราง และข้อมูลที่จับก่อนแก้
- Godot `match_fish`: 16 checks รวม async bite gate, cancel ระหว่างรอ, JSON จริง,
  การลบปลาของคนอื่น การคืนปลา และ deterministic restock/reconnect
- Competition gameplay headless และ rendered: 16 ข้อต่อแบบผ่าน
- กรณี offline/lure ใช้เส้นทางเดิมเมื่อไม่ได้กำหนด bite authorizer
- Regression ออฟไลน์: fishing simulation 60, lure control 72, lure rhythm 238 ผ่าน

## สถานะติดตั้ง

ติดตั้ง migration 013 บน Lakebound แล้ว ย้ายปลาที่จับแล้วที่ระบุได้ 3 ตัวเป็น consumed
โดยไม่ลบหรือคำนวณคะแนนเดิมใหม่ Guest ไม่ได้รับสิทธิ์เรียก match RPC
Production smoke `exclusive_fish_smoke_passed` ตรวจเจ้าของหนึ่งคน การปฏิเสธอีกคน
และผลจับซ้ำ แล้ว rollback fixture ทั้งหมด
Godot HTTP probe ด้วยบัญชีที่ล็อกอินอยู่ผ่าน `fish_ownership_protocol` และ `valid_http_snapshot`
เปิดสองหน้าต่างรุ่นแก้แยกโปรไฟล์ให้ผู้ใช้ทดสอบจริงต่อ ยังไม่อ้างว่าทดสอบหลายอุปกรณ์ครบทุกกรณีแล้ว
