# ประวัติแบบจำกัดและ Ranking

## ข้อมูลในเครื่อง

- `journal` เก็บ 10 ตัวน้ำหนักมากที่สุดต่อชนิดจากทุกแผนที่ ตัดสินน้ำหนักเป็นกรัม แล้วเวลาจับก่อนและ catch ID
- `history.stats` เก็บ count/total/best/smallest/last ของทุกตัวที่เคยจับ แม้ตัวนั้นไม่ติดสิบอันดับ
- `history.map_bests` เก็บสรุปหนึ่งสถิติต่อแผนที่/ชนิด เพื่อไม่ให้สถิติแผนที่หายเมื่อไม่ติดสิบอันดับรวม
- จำนวนพิชิตจ้าวบ่อเก็บใน `boss_counts`; รายละเอียดจ้าวบ่อไม่เก็บตัวอื่นนอกสิบอันดับชุดเดียวกัน
- ปลาในกล่องที่ยังไม่ได้ขาย/ปล่อยเป็น inventory จริง จึงไม่ลบทิ้งตามกฎประวัติ
- บันทึกเก่ารุ่น 1 ย้ายข้อมูลในหน่วยความจำก่อน บันทึกแบบ atomic เมื่อ commit สำเร็จ ไม่มีการแก้ไฟล์เซฟผู้เล่นจริงระหว่าง QA

ก่อนลบข้อมูล recovery ต้องให้ collection บันทึกยอดสะสมสำเร็จ และ profile ยืนยันการรับทราบแล้ว
`history.pending` เป็นคิวกู้คืนชั่วคราว ไม่ใช่ประวัติถาวร ปกติว่างหลังตกปลาเสร็จ หากบันทึก collection ล้มเหลว
จะเก็บรายการนั้นไว้แม้เป็นปลาตัวเล็ก แล้ว replay เมื่อเปิดใหม่โดยไม่นับซ้ำ
เซฟเก่าขนาดใหญ่อาจมี pending จำนวนมากเฉพาะระหว่างการย้ายข้อมูลครั้งแรก
ID ที่ใช้ป้องกันการส่ง event ซ้ำเก็บแบบจำกัด: profile มี 128 รายการล่าสุด และ collection ย่อ ledger เมื่อเกิน 512
หลัง profile รับทราบการบันทึกแล้ว โดยยังเก็บ ID ของประวัติสิบอันดับไว้

## ความถี่และการซิงก์

การจับปลาและ `profile.changed` ไม่มีการเรียก HTTP ข้อมูลถูกบันทึกในเครื่องตาม transaction เดิม
ส่งเมื่อเปิด Ranking, เปลี่ยนมุมมองในบอร์ด หรือกดอัปเดตเท่านั้น การปิดบอร์ดยกเลิก retry timer
ไม่มีการ poll อัตโนมัติหลังได้คำตอบสำเร็จ

Google Sheets endpoint ใช้ `SheetsRankingSync`:

1. ส่งเฉพาะสถิติใหม่/ยังไม่ได้ตอบรับ สูงสุด 100 รายการต่อชุด ชื่อผู้เล่นส่งเฉพาะครั้งแรกหรือเปลี่ยนชื่อ
2. ชุดสุดท้ายใส่ `query` ระบุ map/limit/version ใน POST เดียวกัน Apps Script เปรียบเทียบ บันทึก ปลดล็อก
   แล้วสร้าง snapshot ที่เปลี่ยนและคืนอันดับทันที ไม่ต้องรอ trigger ห้านาที
3. เมื่อไม่มีข้อมูลใหม่ใช้ GET ดูอันดับจากแคช ไม่ผ่านคิวเขียน ไม่ส่ง guest token
4. เก็บ acknowledgement ลง `user://sheets-ranking-sync.cfg` เฉพาะเมื่อได้คำตอบถูกต้อง เพื่อไม่ส่งซ้ำหลังเปิดเกมใหม่
5. รับเฉพาะข้อมูล tuple schema 3 และใช้ catalog ในเกมแสดงชื่อปลา/แผนที่ เก็บ cache อันดับในหน่วยความจำ
   และบันทึกลง `user://sheets-ranking-views.cfg` สูงสุดหนึ่งชุดต่อแผนที่/อันดับรวม รวมไม่เกิน 7 ชุด × 100 แถว
   เมื่อเปิดบอร์ดจะแสดงข้อมูลที่บันทึกไว้ทันทีพร้อมระบุว่ากำลังอัปเดต ไม่อ้างว่าเป็นข้อมูลสด
6. หากระบบแน่น/เครือข่ายล้มเหลว รอแบบสุ่มและ exponential backoff สูงสุดสามครั้งขณะยังเปิดบอร์ด
   ไม่มีการลองใหม่แบบไม่จำกัด และจะไม่ลบสถิติที่ยังส่งไม่สำเร็จ

ตัวเชื่อมเดิม `/sync` ยังทำงาน โดยการเปลี่ยนตัวกรองไม่ส่งสถิติที่ server ตอบรับไปแล้วซ้ำในรอบเปิดเกมนั้น
ตั้ง URL เริ่มต้นใน `online.cfg` เป็น Google Web App แล้ว ค่า override ที่ผู้ใช้เคยตั้งในเครื่องยังมีลำดับสูงกว่า
ตัวเกมตาม redirect ของ Apps Script ไปยัง Google content host ด้วย GET ใหม่ โดยไม่ส่ง body/token ซ้ำ
ผู้เล่นที่ยังไม่มีสถิติใหม่ไม่ต้องสมัคร guest เพื่ออ่านอันดับ จึงเปิดครั้งแรกด้วย GET สาธารณะได้
เมื่อมีสถิติจริงค่อยส่ง POST พร้อมชื่อ/guest token และรับทราบการบันทึกตามเดิม

## หน้าจอ

เปิด `features/social/social_panel.tscn` เพื่อแก้หน้าจอใน Editor มีอันดับรวม รายแผนที่ทั้งหก และ Top10/50/100
แสดงยอดสะสมแยกจากจำนวนประวัติที่เก็บ และแยกสถานะ offline/local จากอันดับออนไลน์
Google snapshot ปัจจุบันมีเฉพาะรวม/รายแผนที่ จึงปิดตัวเลือกอันดับรายชนิดบน Google endpoint
ส่วน server เดิมยังรองรับตัวกรองรายชนิดตามเดิม
รายละเอียดย้อนหลังของปลาที่ไม่ติดสิบอันดับ เช่น หมายเหตุ/จุดจับเฉพาะรายการนั้น จะไม่ถูกเก็บเป็นประวัติถาวร

## การทดสอบ

ชุด catch_archive ทดสอบย้าย 1,050 รายการ เก็บสิบอันดับแต่ละชนิด ยอดสะสม/ยอดจ้าวบ่อไม่ลด
สถิติแผนที่ที่ไม่ติดสิบอันดับยังอยู่ กู้คืนปลาตัวเล็กหลังไฟล์ collection เขียนไม่สำเร็จได้ และ rollback ได้
ชุด sheets_ranking_sync ทดสอบไม่มี HTTP ตอนจับปลา ส่งเฉพาะ delta, acknowledgement หลังเปิดใหม่,
สถิติใหม่ระหว่าง request ไม่หาย, GET เมื่อไม่มี delta และ retry แบบจำกัด
ชุด ranking_maps ตรวจหกแผนที่ ตัวกรอง/Top N และ layout ที่ 960×540, 1280×720, 1600×720

## เป้าหมาย 100 คำขอพร้อมกัน

เอกสาร Google ระบุ simultaneous executions 30 ต่อผู้ใช้ และ 1,000 ต่อสคริปต์:
https://developers.google.com/apps-script/guides/services/quotas

เว็บแอปแบบ execute as owner ใช้สิทธิ์ของเจ้าของ:
https://developers.google.com/apps-script/guides/web

จึงยังไม่รับรอง 100 executions พร้อมกันผ่านบัญชีเจ้าของ คำขออ่านที่มี cache ไม่ใช้ write lock
แต่การเขียนต้อง serialize เพื่อป้องกันข้อมูลทับกัน จำนวนผู้เล่นออนไลน์ไม่เท่ากับ executions พร้อมกัน
การยืนยัน burst 100 คำขอต้องยิงไปยัง Web App ที่เผยแพร่จริงและวัด success/failure/latency
ไม่ใช้การทดสอบ handler แบบลำดับเดียวกันมาอ้างว่าเป็นผล concurrent HTTP

ทดสอบ `services/google_sheets/load_test.py` กับ Web App ที่เผยแพร่จริงแล้ว: อ่านพร้อมกัน 100 คำขอ สำเร็จ 100/100
ไม่ retry, median 5.641 วินาที, p95 7.547 วินาที, รวม 9.0 วินาที กระดานยังว่างและ JSON ตอบกลับ 57 ไบต์ต่อคำขอ
ผลอยู่ใน `exports/qa-sheets-live/load-100.json` และ HTTP POST/GET smoke test ผ่าน 7 ข้อโดยไม่เพิ่มคะแนนทดสอบ
Godot HTTPS จริงผ่านการสมัคร guest แบบไม่มีคะแนน เปิดบอร์ดซ้ำด้วย GET เลือกแผนที่ และขอ Top100
ผล load test แบบอ่านไม่ใช่การรับรองการเขียน 100 รายการพร้อมกัน หากต้องรับประกันระดับนี้ควรพิจารณา
managed serverless backend ที่มี concurrency/queue ควบคุมได้ โดยยังใช้ชีตเป็นหน้าดูแลข้อมูลได้

### เปิดอันดับจากในแผนที่

HUD ร่วมของทั้ง 6 แผนที่มีปุ่ม “อันดับแผนที่” ใต้ minimap และวางกล่องภารกิจถัดลงมา
ปุ่มเรียก `SocialPanel.open_for_map(controller.map_id)` ซึ่งเลือกโหมดและแผนที่ก่อนเริ่ม sync
จึงไม่ส่งคำขออันดับรวมก่อนเปลี่ยนเป็นแผนที่ ผู้เล่นเลือก Top 10/50/100 ต่อได้ในหน้าต่างเดิม
หน้าต่างเข้าระบบ modal ของ HUD เพื่อพักการควบคุมเกมและคืนสถานะเมื่อกดกลับ
SocialPanel ใช้ process mode Always เพื่อรับปุ่มและ HTTP ขณะเกมพัก โดยยังคงส่งข้อมูลเมื่อเปิดบอร์ดเท่านั้น

ตรวจด้วย `hud_session` (ปุ่มทั้ง 6 map IDs และ pause/resume), `ranking_maps`
(filter, Top N, ข้อมูลอันดับ และขนาดหน้าจอ), `compact_hud` (แตะเปิด/ปิดและพื้นที่ปุ่ม),
รวมถึง `social_profile` และ `sheets_ranking_sync` โดยใช้ข้อมูลทดสอบแยกจากผู้เล่นจริง
