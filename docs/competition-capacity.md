# เตรียมขยายสำหรับ 300 คนต่อเดือน

อัปเดตภายหลังในวันเดียวกัน: เกมรุ่นปัจจุบันใช้ Cloudflare สำหรับห้องใหม่แล้ว ดู [competition-cloudflare.md](competition-cloudflare.md) เอกสารนี้อธิบายเส้นทาง Supabase เดิมที่ยังใช้เมื่อ rollback เท่านั้น

เป้าหมายคือผู้เล่นไม่ซ้ำ 300 คนต่อเดือน เริ่มด้วยเพดาน 4 ห้อง ห้องละ 2–5 คน รวม 20 คนพร้อมกัน ไม่ใช่ 300 คนพร้อมกัน และไม่ใช่การรับประกันใช้ฟรีไม่จำกัดเวลา

## นโยบายที่นำไปใช้

- Migration `202611030016_match_capacity.sql` เพิ่มเพดานจาก 1 ห้อง/5 คน เป็น 4 ห้อง/20 คน โดยรักษาข้อมูลและยอดจองเก่า
- WebRTC ยังส่งตำแหน่งได้สูงสุด 20 Hz เมื่อทุกลิงก์ในห้องพร้อม ห้องใหม่และ rematch ใช้ Broadcast สำรองทุก 2 วินาที แทน 334 ms จึงอาจเห็นคนอื่นเคลื่อนไหวไม่ต่อเนื่องหาก RTC ใช้ไม่ได้
- จองโควตาห้องใหม่ `(วินาทีการแข่งขัน + 180) × 15` events ต่อรอบ โดยเผื่อห้องเต็มห้าคนแม้มีผู้เล่นน้อย การสร้างซ้ำ/เข้าห้องด่วนไม่จองซ้ำ
- งบคงเดิม 1,500,000 events ในหน้าต่างย้อนหลัง 33 วัน ไม่คืนงบจากรอบที่ออกก่อนเวลา งบเต็มจะปฏิเสธรอบใหม่ แต่รอบที่จองไว้แล้วดำเนินต่อและรับผู้เล่นแทนที่ว่างได้
- ห้องเก่าเก็บความถี่และการจองเดิม ถ้ามีห้องเร็ว 334 ms จะยังเปิดห้องเพิ่มไม่ได้จนจบ เพื่อไม่ให้แฟนเอาต์รวมเกินงบ เมื่อ rematch จะเปลี่ยนเป็นนโยบายใหม่
- ล็อก admission เดิมยังกันการแย่งที่นั่ง/งบในหลาย transaction พร้อมกัน ไม่มีการเพิ่มเพดาน TURN credentials เดิม (200 attempts/วัน, 3 attempts/ผู้เล่น/รอบ)
- ไม่เปลี่ยนแพ็กเกจ ไม่สมัครบริการเสียเงินเพิ่ม และไม่เผยแพร่ Android/PWA ในงานนี้

Supabase Free ระบุ 100 realtime events/วินาที, 200 connections และ 2 ล้าน realtime messages/เดือน ห้องสำรองใหม่สี่ห้องจองรวม 60 events/วินาที การจองเป็นแบบจำลอง client ปกติ ไม่ใช่ billing meter และไม่ป้องกัน client ดัดแปลงส่ง Broadcast เกินนโยบาย ต้องดู Usage จริงด้วย

## 300 คนเล่นได้นานเท่าไร

ตัวอย่างเมื่อเริ่มจากงบเต็ม ไม่มีการใช้งานส่วนอื่น/ยอดจองเก่า ทุกคนเล่นหนึ่งรอบ และห้องมีจำนวนผู้เล่นเฉลี่ยตามตาราง:

| คนต่อห้องเฉลี่ย | นาทีต่อรอบ | จำนวนรอบ | events ที่จอง | อยู่ในงบ 1.5 ล้าน |
| --- | --- | --- | --- | --- |
| 5 | 10 | 60 | 702,000 | ได้ |
| 5 | 20 | 60 | 1,242,000 | ได้ |
| 2 | 10 | 150 | 1,755,000 | ไม่ได้ |

จากงบเต็ม จองรอบละ 10 นาทีได้ 128 รอบ หรือสูงสุด 640 ที่นั่งต่อรอบ หากครบห้าคนเสมอ เท่ากับเวลาเล่นรวมประมาณ 106.7 ชั่วโมงผู้เล่น ดังนั้นผู้เล่น 300 คนเข้าเล่นเป็นครั้งคราวทำได้ในแบบจำลองนี้ แต่คนละชั่วโมงทุกวันไม่ได้ การใช้ RTC จริงอาจน้อยกว่างบจองมาก แต่ยังไม่ลดการจองตามคำกล่าวอ้างของ client เพื่อเลี่ยงเสี่ยงเกินโควตา

## การดูแลและขั้นขยายต่อ

เจ้าของเรียกใน SQL Editor ได้:

```sql
select jsonb_pretty(public.lakebound_capacity_status());
```

ผลประกอบด้วยเพดาน จำนวนห้อง/ผู้เล่นที่มี lease ยังใช้ได้ ยอดจองคงเหลือใน 33 วัน และ TURN issuance attempts วันนี้ ไม่มี credentials หรือข้อมูลผู้เล่น ฟังก์ชันจำกัดเฉพาะเจ้าของ/server role

เมื่อใช้งบจองเกิน 70% ให้ตรวจ Usage ของ Supabase และ Cloudflare ร่วมกับเวลาเล่นจริง ถ้าเกิน 90% ให้เตรียมลดการรับรอบใหม่ เครื่องมือนี้รายงานเมื่อเรียกดู ยังไม่มีการแจ้งเตือนอัตโนมัติหรือ hard spending cap ฝั่ง Cloudflare

หยุดรับผู้เล่น/รอบใหม่โดยให้รอบปัจจุบันเล่นต่อ:

```sql
update lakebound_private.match_limits set accepts_new=false;
```

เปิดรับอีกครั้งด้วย `accepts_new=true` ลดเพดานด้วย `max_rooms=1,max_players=5` ได้โดยไม่ลบข้อมูล ผู้เล่นที่ lease หมดจะต้องผ่าน admission ใหม่ ไม่ควรลดเพดานกลางช่วงผู้เล่นหนาแน่น

ขั้นถัดไปก่อนเปิดเกิน 20 คน: ทดสอบจริงต่างเครือข่ายและมือถือครบห้าคน/ห้อง เก็บ latency/error/RTC success rate และ egress ต่อชั่วโมง วัด hosted load หลายห้อง แล้วจึงพิจารณา backend/metering เพิ่ม ห้ามใช้ผล PostgreSQL ในเครื่องแทนการรับรองประสิทธิภาพ Supabase Free

แหล่งโควตาที่ตรวจ 3 พฤศจิกายน 2026: https://supabase.com/docs/guides/realtime/limits , https://supabase.com/pricing , https://developers.cloudflare.com/realtime/turn/faq/

## ผลการตรวจและใช้งานจริง

- Deploy migration 016 บน Supabase Lakebound แล้ว ยืนยัน `max_rooms=4`, `max_players=20`, `accepts_new=true` ผ่านรายงานจากฐานข้อมูลจริง
- ณ การตรวจหลัง deploy: ยอดจองเดิม 408,600 เหลือ 1,091,400 events จาก 1,500,000 ใน 33 วัน ตัวเลขนี้คือการจอง ไม่ใช่ยอด Usage จริงจากผู้ให้บริการ
- PostgreSQL ชั่วคราวในเครื่องผ่าน 202 checks รวม regression เดิมและ 21 บัญชีทดสอบ: เข้าพร้อมกัน 16 คนเพื่อเติมสี่ห้องเป็น 20 คน, ขอ snapshot พร้อมกัน 20 คนสามระลอก, ลงทะเบียน/อ่าน RTC signaling พร้อมกัน 20 คน, กันห้องที่ห้า/ข้ามห้อง/จองงบแข่งกัน และตรวจ fallback ของห้องเก่า
- Godot native WebRTC ผ่าน 19 checks เปิด mesh ห้าผู้เล่นครบยี่สิบ directed DataChannels พร้อมตรวจ 20 Hz ไม่ส่ง Broadcast ซ้ำ และ fallback สองวินาที ผลทดสอบในเครื่องไม่ใช่การรับรอง latency ของผู้เล่นยี่สิบคนต่างเครือข่ายหรือมือถือ
- รันซ้ำด้วย `node services/supabase/test_matches.cjs` และ `node tools/test_competition.cjs match_webrtc` ใช้โปรไฟล์/คลัสเตอร์ทิ้งได้ ไม่รัน load test เขียนข้อมูลผู้เล่นจำลองบน production
