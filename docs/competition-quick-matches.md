# ห้องด่วน เวลา กติกา และการควบคุมโหลด

## พฤติกรรม

ผู้สร้างเลือกสนาม เวลา 3/5/10/15/20 นาที และกติกาก่อนสร้างห้อง เปลี่ยนไม่ได้กลางรอบ
ล็อบบี้ ผลแข่ง และ HUD แสดงเวลา/กติกาของห้อง
หาห้องด่วนเข้าห้องที่สร้างก่อน ยังว่าง เจ้าของออนไลน์ และยังไม่เริ่ม
ไม่มีห้องให้แจ้ง ไม่สร้างห้องโดยไม่ตั้งใจ ส่งซ้ำหลังเน็ตหลุดกลับห้องเดิม ไม่เพิ่มสมาชิกซ้ำ
ทุกคนกดพร้อมแล้วเจ้าของเริ่ม ผ่าน loading barrier เดิมเพื่อเริ่มพร้อมกัน

| กติกา | คะแนนที่ Supabase คำนวณ |
|---|---|
| น้ำหนักรวมปลาชนิดที่กำหนด | รวมทุกตัวของชนิดที่เลือก ต้องเป็นปลาที่มีในสนามนั้น |
| น้ำหนักรวมปลาทุกชนิด | รวมทุกตัว ทุกชนิด ไม่จำกัดแค่ 3 ตัวหนักสุด |
| ปลาตัวใหญ่ที่สุด | ตัวที่หนักที่สุดเพียงตัวเดียว ไม่จำกัดชนิด |

คะแนนเท่ากันได้อันดับร่วม ไม่ใช้ปลาอื่นตัดสิน เวลาและการรับคะแนนใช้เวลาฐานข้อมูล
ผลซ้ำไม่เพิ่มคะแนน แข่งใหม่กลุ่มเดิมใช้เวลา/กติกาเดิม
ห้องก่อน migration 011 คง top-three เพื่อไม่เปลี่ยนผลย้อนหลัง ต้องสร้างห้องใหม่เพื่อเลือกกติกาใหม่

## เพดานช่วงทดสอบ

ตรวจเอกสาร 2 พฤศจิกายน 2026: [Realtime limits](https://supabase.com/docs/guides/realtime/limits)
ระบุ Free 200 connections / 100 events ต่อวินาที;
[Realtime messages](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages)
ระบุ 2 ล้าน messages ต่อรอบบิล Broadcast นับการส่งและการรับของแต่ละสมาชิก
200 จึงไม่ใช่จำนวนผู้เล่นที่รับรองได้ ต้องพิจารณาความถี่และจำนวนคนต่อห้องด้วย

- เริ่มที่ **4 ห้อง / 20 ตัวตน Google พร้อมกัน** ห้องละ 5 คน ตรวจใน RPC ภายใต้ lock เดียวกัน
- Pose คนละไม่เกินหนึ่งครั้งทุก 2 วินาที: เต็ม 4 ห้อง × 5 คน × 5 events / 2 วินาที = 50 events/วินาที
  เหลือพื้นที่สำหรับ heartbeat/join/บริการอื่น ไม่ส่ง pose นอก running
- WebSocket เฉพาะ loading/countdown/running; HTTP poll ทุก 5 วินาที
- RPC ต่อบัญชีไม่เกิน 6 ครั้ง/วินาที client รวมคำสั่งซ้ำและ retry แบบ backoff พร้อม jitter
- Lease ที่นั่ง 75 วินาที client หยุดส่ง/ปิด Realtime เมื่อไม่มี RPC ยืนยันเกิน 45 วินาที
  ผู้กลับมาหลัง lease หมดต้องผ่านเพดานใหม่ ช่อง private ต้องมีสมาชิกและ lease ที่ยังไม่หมด
- สำรองงบย้อนหลัง 33 วัน UTC ก่อนสร้างห้อง/แข่งใหม่ `(duration + 180) × 15` events ต่อรอบ
  ประเมินห้องเต็ม 5 คนพร้อม control margin ไม่คืนส่วนไม่ได้ใช้ จึงปิดรับเร็วกว่าการใช้จริงได้
  เพดานสำรอง **1.5 ล้าน events/33 วัน** ไม่รีเซ็ตต้นเดือน จึงไม่เปิดงบใหม่ก่อนรอบบิลจริง ส่ง create ซ้ำไม่หักซ้ำ
- เต็มแล้วปฏิเสธห้อง/ผู้เล่นใหม่พร้อมข้อความ รอบที่สำรองไว้แล้วเล่นต่อได้
- เจ้าของปรับลด `lakebound_private.match_limits` หรือปิดรับด้วย `accepts_new`
  ผู้เล่นไม่มีสิทธิ์อ่าน/เขียน limits, leases, budget, requests

นี่เป็นการจำกัด traffic ของ client เกมตามโปรโตคอล ไม่ใช่เครื่องวัดโควตาจริงของ Supabase
ไม่ครอบคลุมบริการอื่น หลาย socket จากตัวตนเดียว client ดัดแปลง หรือ traffic โจมตี
ต้องดู Dashboard Usage/Realtime Reports ร่วมด้วย Provider ยังบังคับเพดานจริง
ไม่ได้ปรับ billing หรือขยายสิทธิ์ ไม่ถือว่าเป็น load test 20 อุปกรณ์จริง

### แก้ตัวตรวจ JSON หลังทดลองจริง

Godot JSON decoder อ่านจำนวนเต็มจาก wire เป็น float; `600.0 in [180,300,600,900,1200]`
ไม่ผ่านเพราะ Array membership แยกชนิด int/float แม้ค่าจะเท่ากัน
ตรวจว่าเป็นตัวเลข finite ไม่มีเศษและอยู่ในช่วงก่อนแปลงเป็น int เพื่อเทียบค่าที่อนุญาต
เพิ่ม JSON round-trip regression (ยืนยันล้มเหลวก่อนแก้) ครบเวลา 5 ค่า × 3 กติกา
และเปลี่ยน fake HTTP ให้ encode/decode JSON จริงเพื่อไม่ให้ข้ามความต่างของชนิดตัวเลขอีก

ตรวจ HTTP จริงผ่าน `tests/match_live_room_probe.gd` ด้วยเซสชัน Google ของบัญชีที่เปิดทดสอบ:
`room_accepted`, `valid_http_snapshot`, `five_digit_code` ผ่าน และยืนยัน duration จาก JSON เป็น float จริง
รายงาน `exports/qa-two-player/real-room-probe.json` ไม่มี token หรือรหัสห้อง
คงห้องไว้ให้ผู้เล่นกลับเข้า ไม่ออกจากห้องหรือลบข้อมูลหลัง probe
Regression ที่เกี่ยวข้อง: competition 23, match_options 33, transport 12 ผ่านทั้งหมด
